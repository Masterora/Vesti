# Vesti 首个正式版交付计划

## 完成定义

本计划的“最终完成”指：需求方与工作者可用真实钱包在一个明确支持的 Solana 网络上，完成创建合约、申请或指定工作者、USDC 注资、交付、修改、批准、付款及双方同意的争议结算；应用与链上资金状态可核对，服务故障后可恢复，部署和运营流程可重复执行，并通过正式版安全验收。

范围沿用现有 MVP：经典 SPL Token Program 和单一 USDC Mint。法币、KYC、法律仲裁、多链、Token-2022 和开放式市场扩张不计入这六轮。迭代 1 在现有程序所有资金入口统一落实经典 Token 限制；若发现已部署的 Token-2022 托管账户，必须先设计兼容退出，不能使其结算路径失效。若目标市场的法律审查要求额外能力，必须先单独确定产品范围，不能把本计划视为合规结论。

当前基线是提交 `f436ad4`：迭代 1 的链上争议结算、创建前争议方式选择、真实本地验证器程序测试及评审修复已完成；GitHub CI `36546227960` 的 `verify` 与 `onchain` 已通过。Web 注资和付款已有准备、签名、提交、确认及对账，Web 链上争议闭环属于迭代 2。Devnet 程序尚未升级，端到端验收及正式部署尚未完成。每轮保留可运行代码和验收证据；设计文档与对应实现一起提交，不单独提交文档，不把编译成功当作资金行为通过。

## 迭代 1：链上争议资金出口

**目标**：任何参与方发起链上争议后，双方达成有效协议时，资金都有受约束的链上结算或退款路径。

本轮已按用户补充要求增加创建前争议方式选择：默认「双方协商」，也可预先指定独立仲裁钱包。指定仲裁钱包可在双方无法达成协议时裁决；两种方式在注资后均不可更改。Web 链上争议入口仍属于迭代 2。

- 定义与 Mock 一致的双方提议、对方接受规则；提议方不能接受自己的方案。链上发起定义为参与方可冻结已注资合约，里程碑 ID 仅作关联标识；Mock/Web 的里程碑状态限制无法由当前链上账户独立证明。明确部分付款及退款终态的可支取余额、后续里程碑状态，以及重复执行的处理方式。
- 在 Anchor 程序实现提议、接受、释放或退款，约束参与方、Mint、金库、收款 Token 账户与累计金额。若新增账户，保持现有托管账户布局的兼容性；在尚未部署的网络上固定程序 ID 与密钥对。
- 用本地验证器执行真正的程序测试，覆盖正常结算、重复结算、非参与方、错误账户、超额付款、交易失败回滚，以及双方达成协议后的资金转出。
- 用实际测试替换 `Anchor.toml` 的占位脚本，并在 CI 加入 Rust 格式、编译及本地程序测试。

**已确认的产品规则**：任一参与方可在链上冻结已注资合约；默认双方协商，无协议时资金持续冻结。创建前也可指定独立仲裁钱包作为另一条资金出口。若必须保证仲裁钱包失联时仍可单方退出，或链上必须校验里程碑状态，需另行调整状态机与承诺方案。

**退出条件**：本地验证器上，两种结算结果都能让资金到达预期账户；失败路径不改变托管余额；同一争议不能二次结算；取消后本金可支取余额为 0。此轮 Web 仍保持链上争议入口关闭。

详细账户、指令、金额模型与测试矩阵见[迭代 1 详细设计](iteration-1-onchain-dispute-design.zh-CN.md)。

## 迭代 2：Web 链上争议闭环

**目标**：真实钱包用户可从页面完成链上争议，且数据库只在链上证据通过校验后推进状态。

- 为发起、提议、接受和指定仲裁人裁决接入准备、签名持久化、广播、确认、对账及状态恢复；所有链上操作共用合约锁，业务状态只在 finalized 证据通过后推进。交付、批准、修改等业务写入也采用统一行锁与锁内复查；构建阶段崩溃通过明确的恢复协议解锁。
- 将链上账户、金额和结果与本地合约及里程碑绑定；直接链上发起而无法映射到本地可争议里程碑时隔离合约、阻止继续付款并进入人工核查。覆盖首次注资及已有初始化账户、构建中断、钱包拒签、页面关闭、RPC 暂时失败、重复点击、并发接受和链上成功但数据库暂时失败。
- 只在端到端流程可运行后启用页面入口，展示交易签名、当前等待状态及需要人工检查的原因。

**退出条件**：本地验证器上，从页面完成争议释放和退款；重启应用或关闭页面后仍能恢复并对账；数据库本金账本与链上证据一致，额外转入 Token 单独核算；相关真实链上数据库集成与浏览器测试通过。

接口、数据迁移、历史重放、并发恢复、页面交互与验收矩阵见[迭代 2 详细设计](iteration-2-web-onchain-dispute-design.zh-CN.md)。本轮实现与本地验收范围见[迭代 2 交付记录](iteration-2-delivery.zh-CN.md)。Devnet、真实钱包扩展、远端 CI 和正式部署仍属后续交付。

## 迭代 3：Devnet 真实交易验收

**目标**：用测试资金证明完整链路，而不依赖 Mock 或伪造 RPC 响应。

- 确定并保管部署密钥与升级权限，使 `Anchor.toml`、程序源码和运行配置的程序 ID 一致；部署精确构建产物并核对链上程序信息。
- 配置经典 SPL 测试 USDC Mint、两个真实钱包和独立 Devnet 环境；逐项走通直接指定与公开申请、注资、提交证明、修改、批准、付款、争议释放与退款。
- 保存每笔签名、程序版本、Mint、预期和实际余额，以及数据库交易和事件记录；验证区块哈希过期、重试、重复付款阻止和对账补偿。
- 对失败用例先修复并重跑，不以单次成功截图替代回归。

**退出条件**：全部约定场景在 Devnet 可重复完成，Explorer 可查到对应交易，链上和数据库余额逐笔一致。部署前后的程序 ID、升级权限和构建产物有记录。Devnet 部署不自动授权 Mainnet 部署。

## 迭代 4：浏览器与双角色验收

**目标**：把“服务能运行”提升为“用户能连续完成任务”。

- 通过真实浏览器和钱包验证需求方、工作者、匿名用户与申请者的可见性及操作权限；覆盖桌面和窄屏。
- 走通完整里程碑流程及取消、争议、断开钱包、切换钱包、刷新页面、失败重试和空状态。确认钱包网络不匹配、余额不足和签名拒绝时的提示及恢复动作。
- 为核心流程建立可重复的浏览器回归；检查键盘焦点、表单错误关联、触控目标和无横向溢出。

**退出条件**：核心流程在目标浏览器和目标钱包中通过，关键异常均有可操作的反馈；浏览器证据与自动化结果单独记录，不与 Devnet 资金验收混写。

## 迭代 5：部署与运营闭环

**目标**：应用、数据库和后台任务在独立环境中持续运行，故障能够发现与恢复。

- 建立可重现的应用部署、数据库迁移、密钥注入、TLS、反向代理来源头约束、备份及回滚流程；先在预发布环境演练。
- 部署定时交易对账和运营数据清理，禁止任务重叠，对失败退出、长时间未对账、余额不一致、RPC 不可用和数据库不可用告警。
- 提供按请求 ID、合约 ID 和交易签名定位问题的操作手册；验证备份恢复、服务重启、RPC 中断和未完成交易恢复。

**退出条件**：从空环境可按文档部署；迁移、回滚、备份恢复和故障演练有记录；健康检查、任务执行及告警在预发布环境真实触发。

## 迭代 6：正式版安全与受控试运行

**目标**：在真实资金进入系统前完成独立审查和有限范围试运行。

- 审查 Anchor 账户约束、权限、重复付款、争议资金出口、升级权限；同时审查 Web 会话、申请者隐私、交易对账、依赖和部署配置。
- 复核迭代 1 已确认的“双方面议、无协议时持续冻结”规则是否满足试点地区的业务与法律要求；若不满足，增加链上方案与验收迭代，不能仅修改运营文案，也不能把双方面议描述成保证自动解冻。
- 将高严重度发现全部修复并复测，确认最终部署字节码对应已审查源码；记录升级、暂停入口、事件响应和密钥轮换责任。
- 以限额和限定参与者运行试点，核对每笔资金、异常处置和客服路径；根据目标市场另行完成必要的业务与法律审查。

**退出条件**：无未关闭的阻断级安全问题；代码、部署产物和运行配置版本一致；试点资金账实相符；运营负责人能执行故障手册。只有此门槛通过，才可把系统称为首个正式版。外部审查和试点发现的问题可能增加迭代，六轮是计划基线而非时间保证。

## 顺序与统一验收规则

| 阶段 | 依赖 | 可对外描述的状态 |
| --- | --- | --- |
| 当前 | Mock 服务闭环、迭代 1 链上争议程序及 CI 已通过，迭代 2 本地 Web 闭环已验证 | 本地资金与 Web 争议闭环；Devnet 及正式部署待完成 |
| 迭代 1–2 | 链上争议可结算，Web 可恢复和对账 | 本地验证器资金闭环 |
| 迭代 3–4 | 测试资金与真实钱包、浏览器验收 | Devnet 验证版 |
| 迭代 5–6 | 运营演练、安全审查、受控试点 | 首个正式版候选；退出条件通过后正式发布 |

每轮至少报告：代码范围、运行命令与结果、真实环境证据、未验证边界、已知风险和回退方式。任何链上部署、生产配置变更或真实资金试点都以明确目标和批准后的实际环境为准；本计划本身不触发这些操作。
